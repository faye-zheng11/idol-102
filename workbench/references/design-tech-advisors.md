# 设计与技术团 —（UI 审美 / UX 交互 / 前后端可行性）

> **什么时候用**：想法和可行性都确认后，你去**写 PRD + 设计原型交互**的时候。
> 和前两支的分工：智囊团问"值不值得做"，用户体验团问"这概念像不像真关系"，**这支落到"具体设计好不好看、好不好用、前后端做不做得出来"**。
> 用法见 `playbooks/design-tech-panel.md`。绑定的 skill 都已内嵌在 `.claude/skills/`。

## 席位

### 🎨 UI / 视觉设计师 — 审美
> 布局层次、色彩情绪、字体排印、留白、打磨。绑定 `arrange`（布局/层次/留白）、`colorize`（色彩）、`typeset`（字体排印）。
> **拷问**：视觉层次对不对（一眼知道看哪）？色彩传达的情绪对不对？字体排印像专业产品还是随便套的？留白够不够、还是挤成一团？

### 🧭 UX / 交互设计师 — 交互感觉
> 流程顺不顺、状态齐不齐、微交互、动效、清晰、防错。绑定 `animate`（动效/微交互）、`critique`（交互挑刺）。
> **拷问**：这个流程点下来顺吗？空/加载/错误/边界状态都设计了吗？动效是有意义还是花哨？会不会让用户犯错、犯了好不好回头？

### 🖥️ 前端工程师 — 前端可行性
> 能不能高质量还原、响应式、可访问性、性能。绑定 `frontend-design`（产出高质量前端）、`adapt`（响应式）、`harden`（生产级健壮/可访问）。
> **拷问**：这个设计前端能不还原走样地做出来吗？各屏幕尺寸/长文本/极端内容撑得住吗？可访问性和性能有没有坑？

### ⚙️ 后端工程师 / 架构 — 后端可行性
> 逻辑、数据、状态机、API、边界能不能支撑。参考 `docs/BACKEND_STORIES.md` + `playbooks/handoff/07-backend-stories.md`（不另用 skill）。
> **拷问**：这个交互背后，后端要维护哪些状态和数据？状态机会不会太复杂？有没有你没想到的边界/失败情况？埋点能不能回答验证问题（对 `docs/tracking/`）？

### 🔍 评审官 — 整体挑刺
> 防止"AI 生成味"、抓最糙的地方。绑定 `critique`（设计评审）、`audit`（质量审计）。
> **拷问**：整体像专业上线产品，还是一眼 AI 味？哪三处最糙、最该先改？

## 每次至少回答

| 席位 | 一句话拷问 |
| --- | --- |
| UI/视觉 | 层次/色彩/字体/留白，哪块拉低了质感？ |
| UX/交互 | 流程顺吗？状态齐吗？会让用户犯错吗？ |
| 前端 | 能不走样还原吗？响应式/边界/可访问撑得住吗？ |
| 后端 | 背后状态/数据/边界撑得住吗？埋点够吗？ |
| 评审官 | 最糙的三处是哪？ |
